# Деплой OQU в продакшен

Платформа хранит загруженные видео на диске, поэтому нужен сервер с **постоянной
файловой системой** — VPS (например PS.KZ, Hetzner, DigitalOcean), а не Vercel.
Всё разворачивается одной командой через Docker Compose: приложение + Postgres.

## Что понадобится

- VPS с Docker и Docker Compose (Ubuntu 22.04+).
- Домен, направленный на IP сервера (для HTTPS).
- 10 минут.

## Шаги

### 1. Скопировать проект на сервер

```bash
git clone https://github.com/flyordie013/Sagatovai.com.git oqu && cd oqu
```

### 2. Заполнить настройки

```bash
cp .env.production.example .env
nano .env
```

Обязательно заполнить:

- `AUTH_SECRET` — сгенерировать: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
- `POSTGRES_PASSWORD` — придумать надёжный пароль для базы.
- `APP_URL` — публичный адрес сайта, например `https://oqu.kz`.
- `BOOTSTRAP_OWNER_EMAIL` и `BOOTSTRAP_OWNER_PASSWORD` — ваш аккаунт владельца
  (создаётся автоматически при первом запуске).

По желанию: `GROQ_API_KEY` (бесплатный ключ включает AI-наставника),
`RESEND_API_KEY` + `EMAIL_FROM` (письма для сброса пароля).

### 3. Запустить

```bash
docker compose up -d --build
```

При старте контейнер сам:

1. применит миграции базы,
2. создаст аккаунт владельца из `BOOTSTRAP_OWNER_*`,
3. поднимет приложение на порту `3000` **только на localhost сервера**.

Проверить: `curl http://127.0.0.1:3000/api/health` → `{"ok":true}`.

### 4. HTTPS

Поставьте перед приложением обратный прокси с автоматическим сертификатом.
Проще всего — Caddy:

```
# /etc/caddy/Caddyfile
oqu.kz {
    reverse_proxy localhost:3000
}
```

```bash
docker run -d --network host -v /etc/caddy/Caddyfile:/etc/caddy/Caddyfile \
  -v caddy_data:/data caddy:2
```

Готово — сайт доступен по `https://oqu.kz`.

### 5. Проверить, что порт 3000 закрыт снаружи

Приложение слушает только `127.0.0.1`, весь трафик обязан идти через HTTPS.
Если порт 3000 доступен снаружи, пароли уходят открытым текстом, а заголовок
`X-Forwarded-For` можно подделать и обойти защиту от перебора.

```bash
# на сервере — должно отвечать {"ok":true}
curl -s http://127.0.0.1:3000/api/health

# с ЛЮБОЙ другой машины (свой ноутбук) — должно быть отказано в соединении
curl -m 5 http://IP_СЕРВЕРА:3000/api/health
```

Второй запрос обязан завершиться ошибкой (`Connection refused` или таймаут).
Если он вернул `{"ok":true}` — порт опубликован наружу: проверьте, что в
`docker-compose.yml` в сервисе `app` строка портов начинается с `127.0.0.1:`,
и перезапустите `docker compose up -d`.

## После запуска

Войдите под аккаунтом владельца → `/admin`:

1. Создайте курсы, модули и уроки.
2. Загрузите видео к урокам (кнопка «Загрузить видео»).
3. Первые 1–2 урока платных курсов отметьте галочкой «Бесплатный урок».
4. В разделе «Геймификация» добавьте цели, достижения и награды.
5. Опубликуйте курсы.

## Сразу после первого запуска — включите бэкапы и мониторинг

Одна команда на сервере — и пять минут в браузере. Без них любая поломка сервера
означает потерю курсов, учеников и видео, а о падении сайта вы узнаете от
клиента.

```bash
cd ~/oqu                          # папка, куда вы клонировали проект
sudo bash scripts/install-cron.sh
```

Дальше — раздел [«Мониторинг»](#мониторинг-узнать-о-падении-раньше-клиентов):
5 минут в браузере, чтобы получать письмо, если сайт лёг ночью.

## Эксплуатация

```bash
docker compose logs -f app      # логи
./scripts/update.sh             # обновление (см. раздел «Обновление платформы»)
docker compose down             # остановить
```

## Бэкапы

Копироваться должны две вещи: **база** (курсы, ученики, оплаты, прогресс) и
**видео**. Обе лежат на одном диске одного сервера, поэтому копии нужны обе — и
лучше ещё и на другом компьютере (об этом ниже).

### Включить одной командой

```bash
cd ~/oqu
sudo bash scripts/install-cron.sh
```

Эта команда:

1. ставит два задания в расписание сервера (cron):
   - **каждую ночь в 03:30** — бэкап базы и видео;
   - **каждые 5 минут** — проверка, что сайт жив (упал — поднимем, см. «Мониторинг»);
2. **сразу делает пробную копию базы** и показывает результат — так вы видите,
   что всё настроено верно, а не узнаёте об этом через месяц.

Команда безопасна: её можно запускать повторно, другие задания в расписании она
не трогает. Выключить всё обратно: `sudo bash scripts/install-cron.sh --remove`
(уже сделанные копии останутся на месте).

### Куда складываются копии

```
/var/backups/oqu/
├── daily/
│   ├── db-2026-08-05_03-30.sql.gz       дамп базы — хранятся 7 последних
│   └── videos-2026-08-05_03-30.tar      архив видео — хранятся 2 последних
├── weekly/                              копии за воскресенье: 4 базы, 2 видео
├── backup.log                           журнал бэкапов
└── healthcheck.log                      журнал самопроверки сайта
```

Старые копии удаляются автоматически — место не забьётся. Скрипт удаляет только
свои файлы и только в этих двух папках.

Каждый дамп проверяется сразу после создания: архив должен открываться и
заканчиваться отметкой Postgres о завершении. Оборвавшийся дамп **не
сохраняется** — вместо него в журнале появляется ошибка. Лучше честно увидеть
«копии нет», чем хранить файл, который не восстановится.

Если видео перестанут помещаться на диск, архив видео будет пропущен, а дамп
базы всё равно сохранится: заполнить диск бэкапом до конца — значит уронить сайт
и остановить базу. В журнале это видно строкой «Мало места».

### Как проверить, что копии делаются

```bash
cd ~/oqu
./scripts/backup.sh --status
```

Пример ответа:

```
Папка бэкапов: /var/backups/oqu (свободно 42.7 GB)
Последний бэкап базы: db-2026-08-05_03-30.sql.gz, размер 12.4 MB, возраст 7 ч
Последний архив видео: videos-2026-08-05_03-30.tar, размер 8.1 GB
Суточных копий базы: 7, недельных: 4
✓ Бэкапы делаются.
```

Если увидите «Свежего бэкапа нет больше полутора суток» — смотрите последние
строки журнала: `tail -n 30 /var/backups/oqu/backup.log`.

Сделать копию прямо сейчас, не дожидаясь ночи: `./scripts/backup.sh`.

### Копия на том же сервере — это ещё не бэкап

Диск может выйти из строя целиком, сервер — пропасть вместе с копиями. Раз в
сутки забирайте папку с бэкапами на другой компьютер. С домашнего компьютера
(или второго сервера):

```bash
rsync -avz root@IP_СЕРВЕРА:/var/backups/oqu/ ~/oqu-backups/
```

Копии здесь только накапливаются: сервер чистит свои старые архивы сам, а на
домашнем компьютере они остаются. Это и нужно — глубина домашнего архива
получается больше серверной. Раз в несколько месяцев удаляйте лишнее вручную.

### Восстановление

Бэкап, который ни разу не восстанавливали, бэкапом не считается. Попробуйте
проделать это один раз спокойно — чтобы не изучать команды в аварийной ситуации.

```bash
cd ~/oqu
./scripts/restore.sh --list                                   # какие копии есть
./scripts/restore.sh --db /var/backups/oqu/daily/db-2026-08-05_03-30.sql.gz
```

Скрипт по шагам:

1. проверяет, что файл копии целый (иначе останавливается, ничего не трогая);
2. спрашивает подтверждение — нужно написать `ДА`;
3. **сохраняет текущую базу** в `/var/backups/oqu/pre-restore-ДАТА.sql.gz` — если
   восстановили не ту копию, можно вернуться обратно;
4. останавливает сайт, заливает копию одной транзакцией (либо всё, либо ничего —
   «наполовину восстановленной» база не останется), запускает сайт;
5. проверяет `/api/health` и говорит, поднялся ли сайт.

Видео восстанавливаются так же:

```bash
./scripts/restore.sh --videos /var/backups/oqu/daily/videos-2026-08-05_03-30.tar
```

Файлы из архива распаковываются поверх существующих; ничего не удаляется.

## Обновление платформы

Обновление меняет и код, и структуру базы. Правильный порядок — сначала копия,
потом сборка, потом миграции, и только в конце переключение сайта на новую
версию. Всё это делает один скрипт:

```bash
cd ~/oqu
./scripts/update.sh
```

Что происходит и почему именно так:

1. **Копия базы.** Если копию сделать не удалось — обновление даже не начнётся.
2. **Свежий код** (`git pull`). Если у вас код уже загружен вручную — запускайте
   с ключом `--no-pull`.
3. **Сборка новой версии.** Занимает несколько минут, и всё это время сайт
   работает на старой версии. Если сборка сломалась — на сайте ничего не
   изменилось.
4. **Миграции базы отдельным шагом.** Изменения структуры базы применяются
   заранее, во временном контейнере, до того как сайт переключится. Каждая
   миграция идёт одной транзакцией: сломанная миграция откатывается целиком, а
   вы узнаёте о проблеме, пока старая версия ещё работает.
5. **Переключение и проверка.** Сайт поднимается на новой версии, скрипт ждёт
   ответа от `/api/health` и сообщает результат. Недоступность — около минуты.

Самопроверка (см. «Мониторинг») на время обновления отключается сама, чтобы не
перезапускать контейнер посреди переключения.

Между шагами 4 и 5 старая версия сайта несколько секунд работает уже с новой
структурой базы — так делают все, но если шаг 4 у вас почему-то не проходит,
можно вернуться к прежнему поведению: `./scripts/update.sh --skip-migrate-step`
(тогда миграции применятся сами при старте нового контейнера, как раньше).

### Если что-то пошло не так

Скрипт сам напечатает три команды. Коротко:

```bash
docker compose logs --tail=100 app          # что именно сломалось
git checkout ПРЕЖНИЙ_КОММИТ && docker compose up -d --build   # вернуть версию
./scripts/restore.sh --db /var/backups/oqu/daily/db-....sql.gz # вернуть данные
```

Номер прежней версии (коммита) скрипт показывает на шаге 2, а путь к копии
базы — на шаге 1. Если сайт не отвечает, но данные целы — восстанавливать базу
не нужно, достаточно вернуть прежнюю версию кода.

### Вручную, если хочется контролировать каждый шаг

```bash
cd ~/oqu
./scripts/backup.sh --db-only          # 1. копия базы
ls -lh /var/backups/oqu/daily/         # 2. убедиться, что файл появился и не пуст
git pull                               # 3. свежий код
docker compose build app               # 4. сборка (сайт ещё на старой версии)
docker compose up -d                   # 5. переключение
curl -s http://127.0.0.1:3000/api/health   # 6. должно быть {"ok":true,...}
```

## Мониторинг: узнать о падении раньше клиентов

Нужны две вещи: внешняя проверка (заметит, даже если сервер выключился целиком)
и локальная самопроверка (сама поднимет упавшее приложение).

### 1. Внешний монитор UptimeRobot — 5 минут, бесплатно

Он раз в 5 минут открывает адрес проверки и, если ответа нет, присылает письмо
или сообщение в Telegram.

1. Откройте [uptimerobot.com](https://uptimerobot.com) → **Register for FREE**,
   заведите аккаунт на свою почту (бесплатного тарифа хватает).
2. Нажмите **+ New monitor**.
3. Заполните:
   - **Monitor type** — `HTTP(s)`;
   - **Friendly name** — `OQU`;
   - **URL** — `https://sagatovai.com/api/health`;
   - **Monitoring interval** — `5 minutes`.
4. В блоке **Advanced** → **Keyword** (если поле доступно): тип `exists`,
   значение `"ok":true`. Так монитор поймает и случай, когда сайт открывается,
   но база отвалилась.
5. В **Alert contacts to notify** отметьте свою почту → **Create monitor**.
6. Проверьте, что оповещения доходят: остановите сайт на минуту
   (`docker compose stop app`), дождитесь письма, запустите обратно
   (`docker compose start app`).

Telegram вместо почты: в UptimeRobot откройте **My settings** → **Add alert
contact** → тип **Telegram** и следуйте инструкции на экране (нужно один раз
написать их боту). Дальше отметьте этот контакт в мониторе.

Почему именно `/api/health`: этот адрес отвечает `{"ok":true}` только если
приложение живо **и** база отвечает. Главная страница может открыться из кэша,
когда база уже недоступна.

### 2. Локальная самопроверка (уже включена)

`scripts/install-cron.sh` ставит проверку каждые 5 минут. Она:

- три раза подряд (с паузами) опрашивает `/api/health` — одиночный сбой во время
  загрузки большого видео не считается падением;
- если сайт действительно не отвечает — перезапускает контейнер приложения и
  пишет об этом в `/var/backups/oqu/healthcheck.log`;
- не перезапускает чаще одного раза в 15 минут: если приложение падает по кругу,
  его нужно чинить, а не дёргать;
- на время `./scripts/update.sh` отключается.

Посмотреть, что она видела:

```bash
./scripts/healthcheck.sh --status        # отвечает ли сайт прямо сейчас
tail -n 30 /var/backups/oqu/healthcheck.log
```

Самопроверка живёт на том же сервере, поэтому при отказе сервера или сети она
молчит — внешний монитор из пункта 1 обязателен.

## Заметки

- Миграции применяются автоматически при старте. `./scripts/update.sh` применяет
  их заранее, отдельным шагом, пока сайт ещё работает на прежней версии. Чтобы
  отключить автоприменение и запускать вручную (`pnpm db:migrate`), задайте
  `RUN_MIGRATIONS=false`.
- Приложение **откажется стартовать без `DATABASE_URL`** в продакшене — это
  защита от случайного запуска на встроенной dev-базе (данные бы стирались).
- Загрузка видео сама откажет с понятным сообщением («На сервере закончилось
  место»), если свободного места меньше 512 МБ или файл в него не поместится —
  недописанный файл при этом удаляется. Порог меняется в `MIN_FREE_DISK_MB`.
  Освободить место помогает `pnpm db:gc-videos --delete` (удаляет видеофайлы,
  на которые не ссылается ни один урок).
- Для масштабирования на несколько инстансов понадобится вынести rate-limit в
  Redis (сейчас он в памяти процесса) — для одного VPS это не требуется.
